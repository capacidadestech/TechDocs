## 1. Objetivo

Establecer las bases técnicas del proyecto **TechDocs** y construir el **andamiaje de toda
la Fase 1**: shell de la aplicación (header + sidebar + layout), el **listado de documentos**,
una **directiva personalizada** y las **pantallas de login** (UI). Opcionalmente un panel de
preview en React.

Este módulo deja lista la **estructura monorepo** (`backend/` + `frontend/` + `services/`),
la **arquitectura de componentes por features** y el **sistema de diseño (SCSS + variables CSS)**,
sobre la que crecen los módulos M2–M5 sin necesidad de re-estructurar.

App de referencia visual: https://document-nest-pro.lovable.app/ (analizada — ver §8)

### 3.2 Estructura del frontend (modular, por features + layouts)

Principio rector: **layouts independientes** (auth vs dashboard) + **features autocontenidas**
con su propio fichero de rutas *lazy-loaded*. Agregar un módulo nuevo = nueva carpeta en
`features/` + su `*.routes.ts`, sin tocar el resto.

> **Nota:** el listado de documentos evolucionó a una **navegación jerárquica de carpetas** (árbol de
> carpetas + tags). El diseño completo de ese modelo vive en
> [`docs/architecture/modelo-documental.md`](../architecture/modelo-documental.md). El árbol
> refleja la estructura **realmente implementada** en M1.

```
frontend/src/app/
├── core/
│   └── theme/theme.service.ts             # ThemeService (paletas + persistencia)
│
├── layouts/                               # SHELLS independientes (cada uno con su <router-outlet>)
│   ├── auth-layout/                        # AuthLayout — pantalla completa, sin sidebar
│   └── dashboard-layout/                   # DashboardLayout — sidebar + header + contenido
│       │                                     (+ colapsar sidebar en escritorio)
│       └── components/
│           ├── sidebar/                     # marca + árbol de carpetas + fila de cuenta
│           ├── header/                      # buscador+filtros (docs) / breadcrumb estático (otras)
│           └── user-menu/                   # avatar + menú (Configuración, Cerrar sesión)
│
├── features/                              # cada feature autocontenida (pages + components + rutas)
│   ├── auth/
│   │   ├── pages/login/                    # LoginComponent (smart, M1 UI · M3 JWT)
│   │   └── auth.routes.ts
│   ├── documents/
│   │   ├── pages/document-list/            # SMART: orquesta árbol + tabla + filtros + modales
│   │   ├── components/                     # presentacionales (dumb) de la feature
│   │   │   ├── breadcrumb/                  # encabezado del panel: ruta de carpetas + título
│   │   │   ├── folder-tree/ · folder-node/ # árbol navegable (recursivo) desde "Inicio"
│   │   │   ├── folder-cards/               # sección "Directorios" (carrusel con flechas)
│   │   │   ├── document-filters/           # popover de filtros (estado / tipo)
│   │   │   ├── status-badge/               # punto de estado palpitante (tooltip)
│   │   │   ├── new-document-form/          # modal SUBIR (dropzone → metadata)
│   │   │   ├── edit-document-form/         # modal EDITAR (ligero)
│   │   │   └── document-detail/            # modal VER (solo lectura)
│   │   ├── services/                       # document · folder · document-filter (mock → API en M2)
│   │   ├── models/                         # document.model · folder.model
│   │   └── documents.routes.ts
│   └── settings/pages/settings-page/       # Configuración (selector de temas)
│
├── shared/                                # reutilizable cross-feature (sin estado de negocio)
│   ├── components/
│   │   ├── data-table/                     # tabla genérica (+ cell-for, table-column)
│   │   ├── paginator/ · empty-state/
│   │   ├── modal/                          # shell de modal reutilizable
│   │   └── confirm-dialog/                 # confirmación (sobre modal)
│   ├── directives/theme-swatch.directive.ts   # appThemeSwatch (directiva custom)
│   └── services/page-header.service.ts
│
├── app.ts                                 # root: solo hospeda <router-outlet>
├── app.routes.ts                          # raíz: monta layouts + carga features lazy
└── app.config.ts
```

> **Decisión:** los modelos y servicios de `documents` viven **dentro de la feature** (no en
> `core/`), por ser dominio propio. `core/` se reserva para singletons transversales (hoy, temas).

### 3.3 Routing modular (escalable y lazy)

`app.routes.ts` solo conoce los **layouts**; cada layout delega en las rutas *lazy* de sus
features. El `DashboardLayout` quedará protegido por `authGuard` en M3.

```ts
export const routes: Routes = [
  {
    path: 'auth',
    component: AuthLayout,
    loadChildren: () => import('./features/auth/auth.routes').then((m) => m.AUTH_ROUTES),
  },
  {
    path: 'dashboard',
    component: DashboardLayout,
    // canActivate: [authGuard],            // ← se activa en M3
    children: [
      {
        path: 'settings',
        loadComponent: () =>
          import('./features/settings/pages/settings-page/settings-page').then((m) => m.SettingsPage),
        data: { title: 'Configuración', crumbs: [/* … */] },
      },
      {
        path: '', // Inicio = listado de documentos
        loadChildren: () =>
          import('./features/documents/documents.routes').then((m) => m.DOCUMENTS_ROUTES),
      },
    ],
  },
  { path: '', redirectTo: 'auth/login', pathMatch: 'full' }, // arranca en el login
  { path: '**', redirectTo: 'auth/login' },
];
```

> **Por qué así:** el login vive bajo `/auth` con su propio shell (sin sidebar); todo lo interno
> vive bajo `/dashboard` con `DashboardLayout`. Las features se cargan *lazy* (prepara M2). La
> ruta `data.folderNav` distingue la vista de documentos (header con buscador) de las demás
> (breadcrumb/título estáticos, p. ej. Configuración). La navegación entre carpetas en M1 es por
> **signal** (`FolderService`); el ruteo por `:folderId` se formaliza en M2.

## 4. Inventario de componentes — Fase 1 (M1–M5)

Se separan **smart (contenedores)** que manejan estado/datos y **presentacionales (dumb)**
que solo reciben `@Input` y emiten `@Output`. Esta separación habilita **OnPush en M5** sin
refactor.

| Componente | Tipo | Ubicación | Estado | Responsabilidad |
|---|---|---|:---:|---|
| `App` (root) | root | — | ✅ M1 | Solo hospeda `<router-outlet>` |
| `AuthLayout` | shell | layouts | ✅ M1 | Shell de autenticación: pantalla completa, sin sidebar |
| `DashboardLayout` | shell | layouts | ✅ M1 | Shell interno: sidebar + header + contenido; colapsar sidebar |
| `Sidebar` | dumb | dashboard-layout | ✅ M1 | Marca + árbol de carpetas + fila de cuenta |
| `Header` | dumb | dashboard-layout | ✅ M1 | Buscador + filtros (docs) / breadcrumb-título estático (otras rutas) |
| `UserMenu` | dumb | dashboard-layout | ✅ M1 | Avatar + menú (Configuración, Cerrar sesión — JWT en M3) |
| `Login` | smart | features/auth | ✅ M1 UI | Formulario de login (Reactive Forms; JWT en M3) |
| `DocumentList` | smart | features/documents | ✅ M1 | Orquesta árbol + tabla + filtros + paginación + modales |
| `Breadcrumb` | dumb | features/documents | ✅ M1 | Encabezado del panel: ruta de carpetas (retroceso) + título |
| `FolderTree` · `FolderNode` | dumb | features/documents | ✅ M1 | Árbol navegable recursivo desde "Inicio" (+ expandir/colapsar todo) |
| `FolderCards` | dumb | features/documents | ✅ M1 | Sección "Directorios": subcarpetas en carrusel |
| `DocumentFilters` | dumb | features/documents | ✅ M1 | Popover de filtros (estado / tipo) |
| `StatusBadge` | dumb | features/documents | ✅ M1 | Punto de estado palpitante con tooltip |
| `NewDocumentForm` | smart | features/documents | ✅ M1 | Modal subir: dropzone → metadata (binario en M2) |
| `EditDocumentForm` | smart | features/documents | ✅ M1 | Modal editar (nombre, directorio, tags, descripción) |
| `DocumentDetail` | dumb | features/documents | ✅ M1 | Modal ver (solo lectura) |
| `DataTable` (+ `cell-for`) | dumb | shared | ✅ M1 | Tabla genérica reutilizable con plantillas de celda |
| `Paginator` · `EmptyState` | dumb | shared | ✅ M1 | Paginación · estado vacío reutilizable |
| `Modal` · `ConfirmDialog` | dumb | shared | ✅ M1 | Shell de modal · confirmación (borrado) |
| `SettingsPage` | smart | features/settings | ✅ M1 | Configuración: selector de temas (vista previa en vivo) |
| `DocumentDetail`/`Form` por ruta | smart | features/documents | M2 | Detalle y formulario completos por `:id` (con archivo real) |

> **Smart/Dumb + `input()`/`output()`:** `DocumentList`, `SettingsPage`, los modales smart manejan
> estado/servicios; los dumb (`DataTable`, `StatusBadge`, `FolderCards`, `FolderNode`, `Breadcrumb`,
> `DocumentFilters`, `Modal`, `ConfirmDialog`, `UserMenu`) solo reciben `input()` y emiten `output()`.
> Esta separación habilita **OnPush en M5** sin refactor.

## 5. Sistema de diseño (SCSS + variables CSS)

Se replica el design system de la app de referencia (DocVault, ver §8) con **SCSS + variables
CSS** — **sin frameworks de estilo**. Los tokens viven en `frontend/src/styles.scss` y se
consumen con `var(--…)` en el SCSS de cada componente.

> **Sin Tailwind:** el plan no lo requiere y los temas débiles del M1 son de Angular, no de CSS.
> Las variables CSS replican el mismo diseño con cero dependencias.

### 5.1 Tokens en `styles.scss` (tema petróleo oscuro)

```scss
:root {
  --radius: 0.5rem;
  --font-display: "Poppins", system-ui, sans-serif;

  --color-background:         #002532; // fondo (teal muy oscuro)
  --color-foreground:         #e3e2da; // texto principal (blanco cálido)
  --color-surface:            #0a3b4a; // paneles y cards
  --color-surface-elevated:   #14505e; // hover de cards
  --color-primary:            #b5b5aa; // marca / acentos (sage)
  --color-primary-foreground: #002532;
  --color-muted:              #2a4f5e;
  --color-muted-foreground:   #a5a59a; // texto secundario
  --color-accent:             #1f4f5e; // estado activo / seleccionado
  --color-accent-foreground:  #e3e2da;
  --color-border:             #2a5a6a; // bordes sutiles
  --color-destructive:        #c45c5c; // acciones destructivas
}

body { background: var(--color-background); color: var(--color-foreground); }
```

Uso en un componente: `.card { background: var(--color-surface); border: 1px solid var(--color-border); }`.

**Iconos de carpeta de colores:** cada directorio recibe un color estable de una paleta
(`FolderService.color()`, derivado del id), para distinguirlos en el árbol del sidebar.

### 5.2 Convenciones

- **Iconos:** SVG inline de [lucide.dev](https://lucide.dev) — igual que la referencia (`file-text`, `search`, `plus`, `upload`), sin dependencia.
- **Tipografía:** `var(--font-display)` (Poppins, Google Fonts) para títulos/eyebrows; `var(--font-sans)` para el cuerpo.
- **Estilo:** minimalista, bordes punteados en zonas vacías, mucho espacio en blanco,
  eyebrows en mayúsculas con `letter-spacing` amplio.
- **Nada de colores literales** en componentes: siempre `var(--color-…)`.

## 7. Detalle de implementación

### 7.1 Modelos `Folder` y `Document`

```ts
export interface Folder {
  id: string;
  name: string;
  parentId: string | null; // null ⇒ carpeta raíz
  createdAt: string; // ISO date
}

export interface Document {
  id: string;
  name: string;
  folderId: string; // hogar (carpeta)
  type: 'pdf' | 'docx' | 'md' | 'xlsx' | 'img';
  status: 'draft' | 'review' | 'published' | 'archived';
  author: string;
  uploadedAt: string; // ISO
  updatedAt: string; // ISO
  size: number; // bytes
  tags: string[];
  source: { kind: 'file' | 'content'; ref?: string; content?: string };
  description?: string;
}
```

> Modelo de dominio completo (relaciones, tags, esquema BD) en
> [`modelo-documental.md`](../architecture/modelo-documental.md).

### 7.2 Layouts (AuthLayout y DashboardLayout)

- `AuthLayout` (**shell**): contenedor a pantalla completa, centrado, sin sidebar ni header. Solo
  un `<router-outlet>` para `features/auth`. **Independiente del dashboard.**
- `DashboardLayout` (**shell**): rejilla `<app-sidebar>` (ancho fijo, **colapsable** en escritorio
  con un tirador) + columna principal con `<app-header>` y `<router-outlet>`. En M3 se protege con
  `authGuard`. Topbar móvil + sidebar off-canvas (responsive).
- `Sidebar` (**dumb**): marca + **árbol de carpetas** (`FolderTree`/`FolderNode` desde "Inicio") +
  fila de cuenta (`UserMenu`).
- `Header` (**dumb**): en la vista de documentos (`data.folderNav`) lleva el **buscador + popover de
  filtros**; en otras rutas, breadcrumb/título estáticos desde `data`.

### 7.3 DocumentList (smart) + DataTable (dumb)

- `DocumentList`: consume `DocumentService` + `FolderService` + `DocumentFilterService`. Filtra por
  **carpeta activa + búsqueda + estado + tipo** con `computed()` y pagina; renderiza en la
  `DataTable` (`@for … track`) con `@if`/`@empty` y `EmptyState`. Orquesta los modales (subir, ver,
  editar, eliminar) y el FAB.
- `DataTable` (**shared, dumb**): tabla genérica reutilizable; columnas por configuración y celdas
  ricas vía la directiva estructural `appCellFor` (`<ng-template appCellFor="…">`).
- `Breadcrumb` / `FolderTree` / `FolderNode` / `FolderCards`: navegación por carpetas (ver §8.2 del modelo).

### 7.4 Directiva personalizada (tema débil principal)

- `appThemeSwatch` (`shared/directives/`): aplica/previsualiza un tema; usa el objeto `host` del
  decorador (no `@HostListener`) para `click`/`mouseenter` y un class binding `is-active`.
- `appCellFor` (directiva estructural de `DataTable`): registra la plantilla de una celda por clave.
- *(El `appHighlight` del plan original no se implementó; el tema débil de directivas queda cubierto
  por estas dos.)*

### 7.5 Login (UI en M1)

- **Reactive form**: email + password con validaciones (`required`, `email`, `minLength`).
- Estado visual de error y botón deshabilitado si el form es inválido.
- En M1 el submit es un *stub*; en **M3** se conecta al endpoint JWT.
- Ruta `/auth/login` con `AuthLayout` (pantalla completa, estilo del design system).

## 8. App de referencia (DocVault) — hallazgos del análisis

Se analizó el HTML SSR, los bundles JS y el CSS del ejemplo:

- **Stack del ejemplo:** React + TanStack Router (SSR), **Tailwind**, iconos **Lucide**, hecho en Lovable.
- **Es una app de UNA sola vista** (rutas `__root__` + `/`): **no tiene login, detalle ni editor**.
  Esas pantallas las añade TechDocs (M2/M3) siguiendo su mismo design system.
- **Modelo del ejemplo:** sube *archivos* (drag-and-drop, `dataUrl`, tamaño en disco). TechDocs
  gestiona *documentos técnicos* por formulario (M2). Conservamos el **look**, no el modelo.
- **Layout:** sidebar `w-72` (marca + carpetas con contador + footer) · main (`max-w-6xl`) con
  header (eyebrow + título display + búsqueda), dropzone y grid de cards.
- **Utilidades extraídas:** formato de tamaño (`B`/`KB`/`MB`) y fecha (`es`, `dd mmm yyyy`).
- Material de referencia descargado en `_bundles/` y `docvault.html`.

## 12. Riesgos y notas

- **Versión Angular:** el PDF asume v17/sintaxis clásica; al ser v22 se adapta a `@if`/`@for`.
- **Fuente:** cargar `Poppins` (Google Fonts) en `index.html` para `--font-display`.
- **Login en M1:** solo UI (form + validaciones + ruta); la autenticación real (JWT, guard,
  interceptor) llega en **M3** — el componente queda preparado.
- **React en M1:** opcional según el cronograma (*"react (uno de los dos)"*); no bloquea el M1.
- **Reubicación del proyecto:** mover Angular a `frontend/` cambia rutas relativas; validar
  `angular.json`, `tsconfig` y scripts tras el movimiento.
- **El ejemplo no es 1:1:** DocVault sube archivos; TechDocs crea documentos por formulario.
  Se copia el sistema visual, no la lógica de upload.
